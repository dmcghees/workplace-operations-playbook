# Case Study: Improving a Workplace Process Through SOP Creation

## Overview

This case study demonstrates how I approach a recurring operational problem, identify the root cause, document the existing process, and turn it into a clear Standard Operating Procedure.

It is based on the type of process improvement and documentation work I have handled professionally. Company specific information, confidential details, and proprietary systems have been generalized.

## The Challenge

Operational problems often appear as isolated mistakes when the real issue is an unclear or inconsistent process.

Common warning signs include:

* The same questions being asked repeatedly
* Important steps being completed differently by different people
* Work depending too heavily on one employee's memory
* Frequent follow up being required
* Deadlines being missed
* New employees struggling to understand the process
* Tasks being lost in email or chat
* No clear ownership
* Recurring errors

In this case, the process had grown over time but had never been formally documented.

## The Goal

The goal was to create a process that was:

* Clear
* Repeatable
* Easy to train
* Easy to audit
* Less dependent on institutional knowledge
* Easier to hand off
* Easier to improve over time

## Phase 1: Identify the Problem

Before writing an SOP, I first determine what is actually going wrong.

Questions include:

* Where does the process usually break down?
* Which steps are unclear?
* Who is involved?
* Where are delays happening?
* What information is missing?
* Which tasks are repeated unnecessarily?
* What happens when the normal process owner is unavailable?

The purpose is to solve the operational problem rather than simply produce documentation.

## Phase 2: Document the Current Process

I map the process as it currently exists.

This may involve:

* Performing the process
* Observing another employee
* Reviewing emails or existing notes
* Interviewing process owners
* Reviewing systems
* Reviewing vendor requirements
* Identifying exceptions
* Identifying approval points

The current process may look something like:

1. Request received
2. Information reviewed
3. Approval requested
4. Vendor contacted
5. Work scheduled
6. Completion confirmed
7. Documentation updated

Even a simple process can contain unclear ownership or hidden dependencies.

## Phase 3: Identify Gaps

Once the current workflow is visible, I look for problems.

Example:

| Process Area | Issue |
| --- | --- |
| Intake | Requests arrive through multiple channels |
| Ownership | No clear person responsible |
| Approval | Approval requirements unclear |
| Tracking | No central status tracker |
| Escalation | No defined escalation path |
| Documentation | Resolution notes inconsistent |

This helps separate process problems from individual performance problems.

## Phase 4: Design the Improved Process

The improved workflow might become:

1. Submit request through one approved channel.
2. Confirm required information is complete.
3. Assign an owner.
4. Determine whether approval is required.
5. Complete or coordinate the work.
6. Track status in a shared system.
7. Escalate when defined conditions are met.
8. Confirm resolution.
9. Close the request with documentation.

The goal is to remove unnecessary ambiguity.

## Phase 5: Define Ownership

Each step should have a responsible owner.

Example:

| Step | Owner |
| --- | --- |
| Request intake | Workplace Operations |
| Financial approval | Manager or Finance |
| Vendor coordination | Workplace Operations |
| Technical work | IT or Vendor |
| Resolution confirmation | Workplace Operations |
| Final documentation | Workplace Operations |

Clear ownership helps prevent tasks from being passed around without resolution.

## Phase 6: Write the SOP

The SOP should include:

* Purpose
* Scope
* Responsibilities
* Required tools
* Step by step instructions
* Decision points
* Exceptions
* Escalation
* Quality checks
* Related documentation
* Revision history

The language should be direct and practical.

## Example Procedure

### Step 1: Receive Request

Confirm the request includes:

* Requestor
* Location
* Description
* Deadline
* Business impact

### Step 2: Review Request

Determine:

* Priority
* Owner
* Required approval
* Vendor involvement
* Expected completion time

### Step 3: Track the Request

Record:

* Date received
* Owner
* Status
* Due date
* Notes

### Step 4: Complete or Escalate

Complete the request when possible.

Escalate when:

* Additional approval is required
* Safety or security is involved
* The issue is outside the team's authority
* A vendor or specialist is required

### Step 5: Close the Request

Confirm:

* Work is complete
* Requestor has been updated
* Documentation is complete
* Follow up items have owners

## Phase 7: Test the Procedure

Before finalizing the SOP, someone else should try to follow it.

Questions include:

* Are any steps missing?
* Is anything unclear?
* Are there assumptions that only the original process owner understands?
* Are the steps in the correct order?
* Are exceptions addressed?
* Does the process work in a real scenario?

The SOP should be revised based on that feedback.

## Phase 8: Introduce the Process

A new procedure is only useful if people know it exists.

Implementation may include:

* Sharing the SOP
* Explaining why the process changed
* Training employees
* Updating forms
* Updating templates
* Updating links
* Clarifying ownership
* Creating a transition period

## Phase 9: Measure the Improvement

Useful measures may include:

* Fewer incomplete requests
* Faster resolution
* Fewer repeated questions
* Fewer missed steps
* Reduced follow up
* Fewer escalations
* Better documentation
* More consistent service

## Example Before and After

### Before

* Requests arrived through email, chat, and verbal conversations.
* Important information was often missing.
* Ownership was unclear.
* Employees asked repeatedly for status updates.
* Completed work was inconsistently documented.

### After

* Requests followed one intake process.
* Required information was defined.
* Every request had an owner.
* Status was tracked centrally.
* Escalation conditions were documented.
* Resolution notes were standardized.

## Continuous Improvement

An SOP should change when the process changes.

Review may be triggered by:

* Repeated employee confusion
* New technology
* Vendor changes
* Policy changes
* Audit findings
* New responsibilities
* Recurring failures
* Organizational growth

The SOP should support the process, not freeze it permanently.

## Key Takeaway

Writing an SOP is not simply documenting a list of steps.

The real value comes from understanding how work is currently being performed, identifying where the process breaks down, clarifying ownership, simplifying the workflow, and creating documentation that makes the improved process repeatable.

The SOP is the final output.

The process improvement work is what makes it valuable.
